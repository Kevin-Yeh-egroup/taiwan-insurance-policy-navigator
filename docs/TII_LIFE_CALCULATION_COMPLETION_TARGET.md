# 人身保險保障數字完整化目標

## 使用者結果

使用者找到正確的保險公司、商品版本與保單後，只需輸入條款所需的保額、單位、計畫別及必要保單狀態，系統就能依事故或保障項目顯示對應的保障數字。

若金額取決於保險公司在事故日、評價日或給付開始日才會確定的資料，系統必須提供明確欄位讓使用者輸入保單或保險公司列示金額，再完成整理；不得從解約金、準備金或其他欄位猜測。

## 版本邊界

- 每筆計算契約以 `source_batch_id + product_id + source document SHA-256` 為邊界。
- 同名商品只要 `product_id`、條款版本或來源文件不同，就分開整理及測試。
- 新候選必須先進入人工來源複核，不得自行覆蓋已核准版本。

## 每個商品版本的完成條件

1. 官方條款來源與版本可驗證。
2. 每個給付、上限、非現金效果及給付方式都有結構化項目。
3. 條款可決定的金額可直接計算。
4. 需要保額、單位、計畫或保單狀態時，畫面提供對應輸入欄位。
5. 需要保險公司報價或事故日資料時，畫面提供精確的列示金額欄位，不使用通用後備值。
6. 互斥事故與條件式附加給付分開計算，不重複加總。
7. 現金給付、非現金效果與給付方式不混入同一保障總額。
8. 條款保障毛額與可能扣除欠費、借款、利息後的實際給付分層呈現。
9. 來源不足或條款無法決定公式時，列出缺少的文件、表格或保單欄位。
10. 通過 exact-version parser、共用計算模型、資料驗證及桌面／手機操作測試。

## 兩層數字完成度

- **條款保障數字已完成**：可依保額、單位或計畫顯示日額、定額、倍數與保障上限。這一層回答「保單寫了多少保障」。
- **事故情境總額已完成**：除條款保障數字外，還能收集住院日數、手術或失能級別、實際費用、既往累計給付與事故時點等條件，計算本次事故的估算總額。這一層回答「這次事故可能給付多少」。

審計與 UI 必須分開呈現兩層；只有日額或上限時，不得標成已完成事故總額。最終理賠仍以保險公司審核為準。

## 版本防錯

- 公開保障摘要只可從已核准的 reviewed ledger 產生，並攜帶 `source_document_sha256` 與 `schedule_sha256`。
- 保單集合重新開啟時，必須用目前摘要重新載入保障表；來源 SHA 缺少或不一致時，不沿用 LocalStorage 內的舊金額。
- `product_id` 可作為內部版本鍵，不必在一般畫面顯示；使用者仍以公司、商品名稱、銷售期間與保單生效資訊核對版本。

## 收斂順序

1. 先複核既有 proposal 與升級 proposal，快速擴大可計算版本。
2. 依商品家族批量建立 deterministic parser，先健康險、傷害險與傳統壽險，再處理投資型與年金。
3. 來源待補與 parser 開發雙軌並行；CAPTCHA 只由人工完成，系統負責批次準備、接續與稽核。
4. 每輪重建計算就緒審計與完成佇列，以「可進入使用者數字流程的商品版本數」作為主要進度，不以 parser 數量代替成果。

### 下一個品質門檻

- Schedule hash 相同只代表 parser 輸出相同；批量人工核准前，仍須產生代表條款與各 exact source 計算條文的差異證據。
- Readiness 後續拆成 `current_reviewed_calculable`、`latest_proposal_pending`、`claim_scenario_ready` 三個維度，避免新版待審時看起來像舊版資料消失。
- 附加條款與批註條款再細分為新增給付、修改公式、修改資格／限額、純投資／行政機制；後者應顯示「不新增獨立現金保障」，而不是零保障。
- 目前有 3 個 `tii-life-027` reviewed orphan records 不在 63,344 筆主資料中；須先查明名單異動、匯入遺漏或批次歸屬，完成前不納入完成率，也不刪除。
